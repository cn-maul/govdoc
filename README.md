# GovDoc —— 公文格式规范化工具

上传一份文档，GovDoc 让大模型读懂它的结构与内容，在**不改动原文一个字**的前提下梳理出正确的章节层次，并按《党政机关公文格式》**GB/T 9704-2012** 输出字号、行距、页边距等格式合规的正式公文 `.docx`。

单文件可执行程序，前端界面已内嵌，双击即用，无需安装运行时。

---

## 它解决什么问题

手头拿到的文档常常是这样的：章节层次混乱、标题层级不一致、编号错乱或重复、段落该属哪一章说不清楚。要把它改成一份能发出的正式公文，通常得逐段读、逐段判断、再手动调格式——既慢又容易漏。

GovDoc 把这件事拆成两步，并且**把"不改变原文"变成机器可验证的事实，而不是一句承诺**：

1. **读懂结构**：把文档解析成带编号的段落清单，交给大模型判断如何归组章节。
2. **按国标排版**：由程序按 GB/T 9704-2012 计算每一个字号、行距、缩进和页边距，输出可继续编辑的 `.docx`。

---

## 「不改变原文」是怎么保证的

这是本项目的核心设计，也是它和"让 AI 重写一遍文档"最本质的区别。

**一句话：原文可以被修改，但每一处修改都必须显式声明、可见、可审计。**

工具需要能修错别字和语病，所以早期"一个字都不许动"的规则改成了上面这条更强、也更有用的规则。
它约束的不是"不能改"，而是**不能偷偷改**——模型能提出的修改变多了，可能静默发生的修改仍然是零：

| 机制 | 做法 |
|---|---|
| **模型只拿编号，不写正文** | 提示词里给模型的是 `编号 \| 类型 \| 原文` 的清单，要求它**只输出编号**来归组。正文文字永远不会由模型直接生成。 |
| **程序按编号取回原文** | 装配阶段从解析结果里按编号取出原文写入成品。这是全程序唯一一处写入正文的地方（`internal/assemble`）。 |
| **要改就必须申报** | 唯一能改写正文的函数是 `docmodel.AppliedText`，它只施加 `Plan.Edits` 里**已声明**的改动，每条都带 `before` / `after` / `reason`。没有任何代码路径可以无条件改写文本。 |
| **校验器拒绝任何丢失/重复** | `docmodel.VerifyPlan` 要求：每个正文段落必须被**恰好引用一次**。少一个（内容丢失）或多一个（内容被复制）都直接判不合格。 |
| **未声明的修改一律拒绝导出** | 导出时 `docmodel.VerifyVerbatim` 拿"原文 + 该段的已声明改动"作为期望值比对：差异若已声明 → 记入改动清单供你审核；**差异若未声明 → 直接拒绝导出**。表格按单元格矩阵比对，图片按字节比对。 |
| **改动逐条可见、可接受/可拒绝** | 网页上每处改动就地显示 `原文 → 改后` 与理由，你可以逐条接受或拒绝，也可以自己新增一条。改错了想还原，一键"拒绝全部"即可回到原文。 |
| **先程序修，再问模型** | 漏收、重复认领、标题悬空这类**可判定**的结构错误，由 `internal/baseline` 先按原文顺序直接修好，并把修了什么写进方案的 `notes`；只有程序修不了的（如引用了不存在的节点）才反馈给模型重做（最多 2 轮）。 |
| **不调用模型也能出方案** | 原文自带层次序数时，「直接生成」按编号直接切章节——这是确定性下限，模型不在线、API Key 没配也能走通。 |
| **结构改动同样可见** | `report` 只保证没丢没重复，看不见**移动**。服务端每次校验都重算「方案 vs 原文自身结构」的差异（`structure`），把换了章节的段落、改名/增删/换位的章节逐条列出。看不懂结构错在哪，正是本工具最危险的失败方式。 |
| **所有非原文文字都列出来** | 成品中每一处不是原文的文字（版头要素、层次序数编号）都会在导出结果里列出，供人工确认"多出来的只有这些"。 |

因此，最坏结果也只是**章节归属不对，或某一处改动你不认同**——绝不会是原文被悄悄改掉。
归属错了界面里改一下即可；改动不认同，逐条拒绝即可；而**原文被悄悄改掉是查不出来的，所以它被代码彻底禁止**。

## 快速开始

### 直接使用

```bash
govdoc.exe
```

启动后按提示打开浏览器（默认 <http://127.0.0.1:8765>）。未配置模型时，**右上角会显示「模型未配置」**，
点它进入设置页，在「模型连接」里填写接口地址、API Key，点「获取模型」后从下拉菜单选择模型；
配置完成后右上角按钮会显示当前模型名。行文方向在「其他设置」页。

**填一次就够了。** 点「保存」后配置会写入 **exe 同目录**的 `govdoc.config.json`，下次直接启动即可继续使用，
不需要重新填写。把整个文件夹拷到别处（甚至拷进 U 盘），配置也跟着走：

```bash
govdoc.exe -settings-path
# 例如：C:\Tools\govdoc\govdoc.config.json
```

也可以用命令行参数或环境变量预先配置（**命令行参数仍然有效**；已保存的设置会覆盖同名参数，
并在启动日志里说明覆盖了哪一项，避免你改了参数却不生效却不知道为什么）：

```bash
# 以 DeepSeek 为例
govdoc.exe -endpoint https://api.deepseek.com/v1 -api-key sk-xxxx -model deepseek-chat

# 或使用环境变量
set GOVDOC_ENDPOINT=https://api.deepseek.com/v1
set GOVDOC_API_KEY=sk-xxxx
set GOVDOC_MODEL=deepseek-chat
govdoc.exe
```

常用参数：

| 参数 | 说明 | 默认 |
|---|---|---|
| `-addr` | 监听地址 | `127.0.0.1:8765` |
| `-endpoint` | 模型接口地址 | — |
| `-api-key` | API Key（也可在界面里填） | — |
| `-model` | 模型名称 | — |
| `-protocol` | `openai-chat` / `openai-responses` / `anthropic` | `openai-chat` |
| `-direction` | 行文方向：`下行文` / `上行文` / `平行文` | `下行文` |
| `-timeout` | 单次模型调用超时 | `120s` |
| `-static` | 从磁盘目录提供界面（前端开发用） | 用内嵌资源 |
| `-no-save` | 不读取也不写入已保存的设置（共享电脑上用） | 关 |
| `-settings-path` | 打印设置文件位置后退出 | — |
| `-v` | 调试日志 | 关 |

> **关于 API Key**：它会随其它设置一起保存到上面那个文件里，这样重启后不必重填。
> **它永远不会回传给浏览器**——界面只知道"已配置"。
>
> 放在 exe 同目录是有意为之：程序与配置放在一起，整个文件夹可以随意搬移。
> 代价是——若该目录不可写（如装在 `Program Files`），保存会失败，界面会明确提示
> "本次已生效，但重启后需要重新填写"，**不会假装存上了**。这时可以加 `-no-save`
> （不落盘），或者把 exe 放到一个可写的目录。
>
> 在 Linux/macOS 上文件权限设为 `0600`（仅属主可读）；Windows 不使用这套权限位，
> 那里的保护来自文件所在目录本身的访问控制。
>
> 上传的文档始终只在内存中处理，不落盘。

## 使用流程

**常规用法只需要两步**：上传 → 点「生成公文文档」。校验通过后会直接生成并下载 `.docx`，不需要人工校对。

1. **上传**：拖入或选择一份 `.docx` / `.txt` / `.md`。左侧会列出解析出的全部段落及类型。
2. **分析**：点「开始分析」。模型返回的章节树连同校验结论一起显示；校验不通过时会指出具体是哪些段落没被收录或重复收录。
3. **生成并下载**：校验通过时，主行动条会给出「生成公文文档」按钮，点击即生成并可下载。页头、校对区顶部与结果卡片三处都有**「下载公文文档」**按钮，任何位置都能直接下载，不用去找。
4. **预览**（可选）：查看按国标排版的 A4 分页效果。被修改过的段落会有高亮，颜色**只做标记，不影响字号与行距**，所以屏幕上的分页与成品一致。
5. **高级校对（可选，默认不阻塞导出）**：左右两栏 —— 左边是成品纸张本身，右边是校正面板，
   右边的任何改动左边立刻重绘，不必来回切页。右栏四个标签：
   - **AI 改动**：模型声明的每一处 `原文 → 改后` 与理由，可逐条接受或拒绝，也可自己新增一条；
     同一页还列出模型对结构的调整（哪段换了章节、哪个章节被改名或换位）。
   - **结构方案**：章节树，可改标题、调整节内顺序、把段落移到其他章节。
   - **原文节点**：每段原文被谁引用；漏收 / 重复一目了然，可就地修。
   - **成文核对**：逐字比对成品与原文，列出缺失、被改写与多出的文本。

   改错了点「拒绝全部」即还原原文。

   每次改动都会重新校验，校验不通过时导出按钮不可用并说明原因。

### 让模型顺手修错别字和语病

分析区有一个「**允许模型修正错别字 / 语病 / 用词**」开关（默认关）。

- **关**（默认）：模型只梳理结构，一个字都不改。
- **开**：模型可以指出并修正错别字、语病、用词不严谨、标点、长句断句，也可以为缺少标题的章节补一个标题。
  但它**必须**为每一处修正给出 `原文 → 改后` 和理由，全部列在改动清单里供你审核。

无论开关是否打开，**没有申报的修改都会导致导出被拒绝**。这个开关放宽的是"模型可以提出哪些修改"，
而不是"哪些修改可以悄悄发生"。

### 用哪套排版规则：格式配置（profile）

工具不再只做公文。公文是**内置的一套格式配置**，此外还有几套通用配置，
你也可以自己新建、改和删。上传文档时选一套，这套规则就套用到标题、正文、行间距、
字体、字号、页边距上。

| 内置配置 | 正文字体 / 字号 | 行距 | 页边距(上/下/左/右) |
|---|---|---|---|
| **公文**（默认） | 仿宋_GB2312 / 三号(16pt) | 固定 28.99pt，每面 22 行 × 每行 28 字 | 37 / 35 / 28 / 26 mm |
| **通用** | 宋体 / 小四(12pt) | 18pt | 25.4 / 25.4 / 31.8 / 31.8 mm |
| **论文** | 宋体 / 五号(10.5pt) | 17pt | 同上 |
| **报告** | 仿宋_GB2312 / 小三(15pt) | 28pt | 同上 |

只有「公文」使用国标的**字符网格**（每面 22 行 × 每行 28 字）。其它配置不启用它——
强加一个文档没要求的网格会把字距压窄，正是标题重叠那类缺陷的成因。

**在设置页里管理配置**（点右上角的模型状态按钮进入，设置页内切到「排版规则」）：

- **内置配置不可直接改或删**。它是所有文档的兜底规则，也是恢复标准样式的依据。
  要调整就先「复制一份」，改副本——原始标准原样保留。
- 副本可以随意修改：标题/正文/各级标题的字体、字号、行距、首行缩进，以及页面尺寸与四边页边距。
- 仍在被某份文档使用的配置不能删除，界面会告诉你有几份文档在用。

**每份文档记住自己用的配置**。你后来改了默认配置，之前上传的文档**不会**被悄悄换规则重排——
否则同一份文件今天导出一个样、明天导出另一个样，而你并不知情。

## 遵循的格式标准

全部格式数值集中在 `internal/gbstandard`，是页面与文件的**唯一来源**——预览和导出的 `.docx` 读同一张表，因此屏幕上看到的就是文件里的。

| 项目 | 取值 | 标准条款 |
|---|---|---|
| 纸张 | A4 210×297mm | §6.1 |
| 页边距 | 上 37、下 35、左 28、右 26mm | §6.1 |
| 版心 | 156×225mm，每面 22 行 × 每行 28 字 | §6.1 |
| 正文 | 三号仿宋（16pt），固定行距 ≈28.99pt，首行缩进 2 字 | §7.3.3 |
| 标题 | 二号小标宋，居中 | §7.3.1 |
| 一级标题 | 三号黑体，「一、」 | §7.3.3 |
| 二级标题 | 三号楷体，「（一）」 | §7.3.3 |
| 三级/四级标题 | 三号仿宋，「1.」「（1）」 | §7.3.3 |
| 发文机关标志 | 红色小标宋，居中；距版心上边缘 35mm（下行/平行文）或 80mm（上行文） | §7.2.4、§4.3.2 |
| 红色分隔线 | 与版心等宽，发文字号下 4mm | §7.2.6 |
| 署名 / 成文日期 | 右空二字 / 右空四字，日期用阿拉伯数字 | §7.3.5 |
| 页码 | 四号宋体，两侧各一条一字线 | §7.3.6 |
| 版记 | 四号仿宋，上下各一条与版心等宽的线 | §7.5 |

**关于「每行 28 字」**：国标同时规定版心宽 156mm 与正文三号（16pt），但 28 × 16pt = 158mm，略超 156mm。国标所附的 Word 模板靠**文档网格**把 28 字钉在行上并轻微压缩字距（约 1.3%）。GovDoc 采用同样做法：以版心宽为准，钉住每行 28 字，压缩字距，**字号仍是三号 16pt**。见 `PageSetup.CharCondensePT`。

启动时程序会检测本机是否安装了所需的公文字体（仿宋_GB2312、黑体、楷体_GB2312、方正小标宋简体等），缺失会给出提示——否则打开文件时会被 Word 静默替换字体。

## 技术栈

| 层 | 选型 |
|---|---|
| 后端 | Go 1.27.3，标准库为主，仅一个第三方依赖 |
| LLM 接入 | [`github.com/cn-maul/rosetta`](https://github.com/cn-maul/rosetta) v1.3.2（统一 OpenAI Chat / OpenAI Responses / Anthropic 三种协议） |
| 前端 | React 19 + TypeScript + Tailwind CSS v4 + HeroUI v3 |
| 分发 | 前端构建产物经 `go:embed` 内嵌，产出单个可执行文件 |
| 文档生成 | 手写 OOXML（`archive/zip` + `encoding/xml`），无第三方文档库 |

界面直接使用 HeroUI v3 组件与 Tailwind 工具类，设计令牌仍集中在 `web/src/styles/tokens.css`（见 `docs/DESIGN_heroUI.md`、`docs/design-tokens.css`）。

校对区是**左预览 / 右校正**的两栏工作台：左边是成品纸张本身（`PreviewPane`，与「分页预览」页共用），右边四个标签分别放 AI 声明的改动、章节结构、原文节点与逐字比对。改动在右侧提交，左侧纸张立刻重绘。

样式按需引入：`web/src/styles/index.css` 只 import 用到的 HeroUI 组件样式（约 330 kB，全量为 734 kB）。新增组件时要补一行，否则「结构对、样式丢」——原因与验证方法见 `docs/DESIGN_heroUI.md` §2。

```
│   ├── store/               内存会话、渲染产物、SSE 作业

│   └── server/              HTTP 服务、SSE 进度、内嵌 UI 托管
├── web/                     React 19 + Tailwind + HeroUI 前端（src/ 源码，dist/ 构建产物）
├── tools/e2e/               端到端验证：跑通全流程并用 python-docx 读回校验
└── docs/                    接口契约、设计规范、设计令牌
```

## 开发与验证

```bash
go build ./...                 # 构建
go vet ./...                   # 静态检查
gofmt -l internal/ cmd/        # 格式检查（应无输出）
go test ./...                  # 单元测试（496 个测试函数）

go run ./tools/e2e             # 端到端：全流程 + python-docx 读回实测
```

`go run ./tools/e2e` 会用一份伪造的"排版混乱"公文跑完「校验 → 装配 → 逐字比对 → 生成 docx → 用 python-docx 读回实测」，并断言：

- 页面 A4、页边距 37/35/28/26mm
- 正文三号 16pt 仿宋、固定行距 ≈28.99pt、首行缩进 2 字
- 标题二号 22pt 居中
- 表格行列正确
- **每一个原文段落都在成品中逐字出现**（这份测试方案不含任何改动声明，因此原文应当一字不差）

它需要 Python 与 `python-docx`（用于独立读回验证），会自动探测可用的解释器。

### 验证真实的 LLM 链路

上面的测试都不需要模型。要验证**含模型的完整链路**（rosetta 客户端 + SSE 进度 + 自修复循环），用仓库里的桩模型：

```bash
# 终端 1：桩模型（OpenAI 兼容，首个回答故意漏收一段以触发自修复）
go run ./tools/stublm -addr 127.0.0.1:8899

# 终端 2：指向桩模型启动 govdoc
go run ./cmd/govdoc -addr 127.0.0.1:8806 \
  -endpoint http://127.0.0.1:8899/v1 -api-key stub-key -model stub-model

# 终端 3：跑真实 HTTP 全流程（上传 → SSE 分析 → 校验 → 导出 → 下载 → 预览）
go run ./tools/httpe2e -addr http://127.0.0.1:8806 -out ./out
```

`tools/httpe2e` 是**真实 HTTP 客户端**（不是进程内 handler），因此它验证的是浏览器实际走的线格式：multipart 上传、EventSource 帧、JSON 结构、`Content-Disposition` 的中文文件名编码。

## 已知边界

- **仅支持 `.docx` / `.txt` / `.md` 输入**。`.pdf` 与旧版 `.doc` 不支持：前者无法保证逐字保真地提取文本，后者需要额外的解析库。遇到这两种格式会明确报错，而不是尝试后产生不可靠的结果。
- **导出仅支持 `.docx`**。这是有意的：公文需要保持可继续编辑，而 PDF 是终态。需要 PDF 时请用 Word/WPS/LibreOffice 另存。
- **工作状态保存在内存中**。进程退出后已上传的文档与已生成的文件都会消失，需重新上传。这样处理公文更安全——不会在磁盘上留下副本。
- **会话与文件有上限**：渲染产物最多保留 32 份，超出后淘汰最旧的；被淘汰的文件重新导出即可。
- **模型的章节判断可能出错**。这正是"校对"步骤存在的原因，也是为什么所有原文内容都被保证不会丢失——判断错了可以改，内容丢了才是不可接受的。
